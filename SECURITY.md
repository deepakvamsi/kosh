# Security Policy

Kosh stores API keys, passwords and other credentials. A vulnerability here is a
vulnerability in the thing people trusted with their secrets, so reports are welcome and
taken seriously.

## Reporting a vulnerability

**Please do not open a public issue for a security report.**

Use either channel:

1. **GitHub Private Vulnerability Reporting** — the *Security* tab → *Report a
   vulnerability*. Preferred, because it keeps the discussion attached to the repository.
2. **Email** — <deepak@nyayasiddhi.com>. Put `KOSH SECURITY` in the subject.

Helpful things to include, in rough order of usefulness:

- What an attacker gains, and what access they need to start (local user? malware already
  running as the user? read access to `vault.db`? physical access?)
- Affected version — the value shown in the app's About, or the release tag
- Operating system and version
- Reproduction steps, or a proof of concept
- Whether the finding involves the encryption, the audit log, the air-seal, or the UI

**Never include real secrets in a report.** Use a throwaway vault with dummy values.

## What to expect

| | |
|---|---|
| Acknowledgement | within 3 business days |
| Initial assessment | within 10 business days |
| Fix or documented mitigation | depends on severity; you will get a timeline, not silence |
| Credit | offered by default in the release notes and `CHANGELOG.md`; say the word if you'd rather stay anonymous |

Kosh is maintained by a small team, not a 24/7 response organisation. There is no paid
bug bounty. Please allow a reasonable window for a fix before public disclosure — 90 days
is the default expectation, and shorter is negotiable if a fix ships sooner or the issue
is already public.

## Supported versions

Fixes land on `main` and ship in the next tagged release. Only the latest release is
supported; there are no long-term maintenance branches.

## Scope

**In scope**

- Recovery of secret material without the master password or recovery key
- Weaknesses in the key hierarchy: Argon2id derivation, DEK wrapping, XChaCha20-Poly1305
  usage, nonce handling, associated data
- Audit log forgery or evidence removal that `VerifyChainKeyed` fails to detect
- Any outbound network connection made by the application (this would break the air-seal
  invariant enforced by `internal/seal`)
- Bypassing the lock screen, auto-lock, or the master-password re-authentication gate on
  recovery-key generation and backup export
- Plaintext leaking to disk, logs, crash dumps, clipboard beyond its configured lifetime,
  or the screen-capture surface
- Cross-vault or cross-user data exposure via file permissions
- Backup archive forgery, or decryption of an archive without its password

**Known and accepted — please don't report these as vulnerabilities**

These are documented design limits, not oversights. See
[`docs/THREAT_MODEL.md`](docs/THREAT_MODEL.md) for the full reasoning.

- **An attacker who copies `vault.db` can attempt an offline brute force.** The only
  barrier is the Argon2id cost. This is inherent to a local, offline, password-protected
  vault. A finding that the *parameters* are too weak, or that the derivation is
  implemented incorrectly, *is* in scope.
- **Malware running as your user account, with the vault unlocked, can read what the app
  can read.** No user-space application defends against an attacker already inside its
  own trust boundary.
- **A privileged process can read the DEK out of the app's memory.** Kosh zeroizes keys
  on lock and on idle auto-lock, but it cannot defeat a debugger running as root or
  Administrator.
- **Audit records written while the vault is LOCKED** (failed unlock, lockout) cannot be
  authenticated — no key exists at that moment — and are hash-chained only. A trailing
  run of such records is a known residual gap.
- **The `ResetVault` operation is deliberately not gated on the master password**, because
  its main legitimate use is "I forgot my password and have no recovery key". It is
  destructive only and cannot exfiltrate plaintext.
- Findings that require a modified build of Kosh, or that assume the user was tricked into
  running a different binary entirely.
- Reports generated by an automated scanner with no demonstrated impact.

## Verifying what you downloaded

Every release publishes `SHA256SUMS-*.txt` alongside the binaries. That proves your
download matches what was published — it does not prove where the binary came from,
because the same workflow generates both.

For provenance, releases also carry a signed build attestation binding each artifact to
this repository, commit and workflow:

```sh
gh attestation verify Kosh-<tag>-windows-amd64.exe --repo <owner>/<repo>
```

Windows builds are Authenticode-signed when signing material is configured; see
[`docs/WINDOWS_TRUST.md`](docs/WINDOWS_TRUST.md).
